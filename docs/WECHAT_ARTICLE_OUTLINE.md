# 公众号文章提纲（工作稿）

## 可用标题方向

- 我为什么不想让 AI 自动保存它自己写的 Skill
- 45 条待审建议之后：我做了一个让 AI 提案先交回执的面板
- AI 会写 Skill，但谁来判断它值不值得留下？

标题中的数量只来自个人当时的一次本地队列，不代表普遍数据；公开前由作者决定是否保留，并且必须先脱敏。

## 叙事主线

1. **起点**：AI 工具会在对话后建议创建 Skill。刚开始以为重点是做一个“采纳/忽略”的审批窗。
2. **实际体验**：用户发现许多对话里生成的 Skill 没有长期用途；逐条审批会把人的注意力浪费在低价值候选上。
3. **转向**：不急着采纳，先生成一份回执，列清楚候选内容和来源，再拿给 GPT 或另一位人类审阅。
4. **做出的第一版**：Hermes 侧栏读待审队列，提供展开、复制、导出；不应用、不删除任何 Skill。
5. **开源调查后的修正**：已有 Skill 管理器、自我演化提案流和 eval 工具。产品不应宣称首创，先诚实做 Hermes 回执适配器。
6. **接下来的问题**：怎样把这张回执标准化，让没有插件入口的 AI 也能通过粘贴/导入使用？怎样用真实效果而非模型自评判断 Skill 是否值得留？
7. **邀请**：征集其他工具用户对回执格式、隐私边界和导入方式的意见。

## 文章发布前检查

- 不贴真实待审 Skill 内容、会话记录、用户名、绝对路径或内部仓库内容。
- 截图先裁掉其他会话、文件名、工作区名称和本机账号信息；改用合成示例更安全。
- 明确区分个人经历、项目功能、未来计划和尚未验证的判断。
- 附开源仓库、许可证、安装步骤和已知限制。
- 避免把“提议数量”写成“有效 Skill 数量”，不要把一次个人队列包装成产品效果数据。
